# 📜 История изменений и разработки

## 💡 Пролог: Поиск подхода (Open WebUI)

* **Эксперимент №1: Использование Open WebUI.**
  * Изначально пытались решить задачу через веб-интерфейсы чата, навязывая модели готовые промпты и шаблоны.
  * **Проблема:** Модели часто галлюцинировали (добавляли лишний markdown), не заходили в контекст Figma и выдавали невалидный код.
  * **Вывод:** Стало очевидно, что для стабильного результата нужен полный контроль над payload и собственная серверная логика.

### 📦 v0.7.0 — Фундамент (структуры данных и протоколы)

**Цель**: зафиксировать контракты между агентами, не меняя модели и движок.

* [ ] **Pydantic-модели** `ComponentTree` / `ComponentNode` — единый контракт для A, B, C и сборщика:
  * `component_id` — уникальный по пути в дереве (`UserCard__Avatar__Icon`)
  * `name` — семантическое имя (`Avatar`)
  * `role` — `atom` / `molecule` / `organism` / `template`
  * `context_role` — где используется (`header_action`, `form_field` и т.д.)
  * `props`, `styles`, `placeholder_text`
  * `parent_applied_styles` — внешние стили, которые родитель применяет к узлу
  * `transit_props` — пропсы для проброса детям (при глубине > 3 — переключаемся на context)
  * `children`
  * _Возможны дополнения_
* [ ] **Скрипт-нормализатор** `component_id` (детерминированный, не LLM): проходит по дереву и присваивает `UserCard__Avatar__Icon` по пути. **Не доверяет LLM уникальность имён.**
* [ ] **Feature flag** `pipeline.isolation_mode` в `config.toml`: Coder получает узел **без `children`**. Позволяет сравнить монолитный и изолированный подходы на одних промптах.
* [ ] **Pydantic-валидация с retry** вместо `format: "json"`: после ответа модели — `model_validate_json`, при ошибке — retry с указанием ошибки в промпте.
  * *Закрывает баг*: «Модель захлёбывается в кавычках при `payload_format="json"`».
* [ ] **Разделить Architect на два вызова** (одна модель, разные системные промпты):
  * Вызов 1: «Аналитик» — разбивает промпт/Figma на слои, определяет иерархию.
  * Вызов 2: «Архитектор» — для каждого узла прописывает пропсы, стили, `context_role`, `transit_props`.
* [ ] **Логирование и воспроизводимость**: сохранять вход/выход каждого агента с хэшем. Для отладки и регрессионных тестов.

### 🧩 v0.8.0 — Изоляция и двухфазная сборка

**Цель**: включить изоляцию по умолчанию и добавить сборку снизу вверх.

* [ ] **Включить `isolation_mode = true`** по умолчанию. Coder получает только свой узел (без `children`).
* [ ] **Агент-сборщик** (отдельный вызов C с ролью «сборщик»):
  * Вход: `parent_json` + контракты **прямых детей** (имя компонента, пропсы, `parent_applied_styles`).
  * Выход: сборочный код родителя (импорты, композиция, передача пропсов).
  * **Не получает** код детей и не видит внуков.
* [ ] **Post-order traversal** (снизу вверх): листья → их родители → ... → корень. На каждом шаге сборщик видит только один уровень.
* [ ] **Разделение «внутренних» и «внешних» стилей**:
  * Внутренние стили ребёнка — уже в его коде (фаза 1).
  * Внешние стили (`parent_applied_styles`) — передаются в контракте, родитель применяет их при сборке.
* [ ] **Контракт на фазе 1**: каждый компонент обязан иметь ровно один корневой DOM-элемент и принимать `className` (React) / `inheritAttrs` (Vue). Явно прописать в системном промпте C.
  * *Закрывает баг*: «При запросе "форма" ИИ-2 генерирует лишний FRAME-обертку».
* [ ] **Prop drilling**: для глубины ≤3 — `transit_props` на промежуточных узлах. Для глубины >3 — `prop_strategy: "context"` в дереве A (React Context / Vue provide-inject).
* [ ] **AST-валидация** после фазы 1 (Babel / Vue compiler-sfc): синтаксис, один корневой элемент, проброс `className`. При ошибке — retry только этого узла.
  * *Закрывает баг*: «Периодически генерирует computed с импортом, без переменной».
* [ ] **`context_role` для B**: B получает `context_role` как read-only метаданные (не меняет, но учитывает при генерации токенов).
  * *Закрывает проблему*: «Слепой дизайн» — Button внутри Header и внутри Form может требовать разных отступов.
* [] AST-валидация перед сборкой: проверка, что каждый сгенерированный компонент имеет ровно один корневой элемент и принимает className (иначе родитель не сможет применить стили).

### ⚡ v0.9.0 — Движок и параллелизм

**Цель**: ускорить фазу 1 (батч изолированных узлов) и добавить constrained decoding.

* [ ] **vLLM / SGLang для фазы 1** (B + C-изоляция):
  * Continuous batching: 15–20 узлов обрабатываются параллельно.
  * `guided_json` через xgrammar/guidance — жёсткая гарантия JSON без retry.

* [ ] **Ollama остаётся для**:
  * Разработки и отладки (быстро, просто, GGUF).
  * Этапа A (Qwen3-30B / DeepSeek-R1 с offload на 12 GB VRAM).
* [ ] **Батчинг**: размер 4–8 узлов (не 20), чтобы KV-cache влезал в 12 GB VRAM. 2–3 волны для 15–20 узлов — всё равно быстрее последовательной обработки.
* [ ] **Детект «узкого места»** (VRAM vs RAM) для выбора квантований:
  * Windows + дискретная GPU: VRAM — главный лимит, offload в RAM.
  * Mac (Apple Silicon): RAM = VRAM (унифицированная память).
  * Ноутбук без дискретки: только RAM, «режим совместимости».
* [ ] **Кэширование по хэшу узла**: если узел не изменился — не генерировать заново.

### 🚀 v1.0.0 — Этап инициализации и стабильный конвейер

**Цель**: проект сам подбирает модели под железо пользователя и работает на Windows / WSL / Linux / macOS.

* [ ] **Детектор железа**:
  * ОС и среда: Windows (нативный / WSL2), Linux (нативный), macOS (Apple Silicon / Intel).
  * VRAM: `nvidia-smi` (Windows/Linux), `system_profiler` (Mac), проверка Intel Arc / AMD.
  * RAM: доступная минус запас ОС.
  * «Здоровье» драйверов: версия NVIDIA, гибридная графика (Intel + NVIDIA) — CUDA видит дискретную карту.
* [ ] **Вилки выбора моделей** (из заготовленных):
  * **≥ 16 GB VRAM**: Qwen3-30B Q4 (A) + Gemma E4B Q8 (B/C). Комфортно.
  * **10–15 GB VRAM** (десктоп пользователя): Qwen3-30B Q3/Q4 с offload (A) + Gemma E4B Q8 (B/C). Этап A медленнее.
  * **6–9 GB VRAM** (типичная игровая GPU): Qwen3-8B / Qwen3-14B Q4 (A) + Gemma E4B Q4 (B/C). Декомпозиция чуть слабее.
  * **< 6 GB VRAM / только CPU** (Zenbook): Gemma E4B Q4 на CPU + Qwen3-8B Q4 на CPU. «Режим совместимости», только для тестов.
* [ ] **Режим «авто» и «вручную»**: проект сам подбирает модели и настройки под железо, либо пользователь выбирает сам.
* [ ] **Предупреждения**:
  * Windows без WSL2: рекомендовать WSL (CUDA через Windows-драйвер, без потери производительности).
  * Mac Intel: только CPU, очень лёгкие модели.
  * Ноутбук без дискретки: «Скорость низкая, рекомендуется только для тестирования».
* [ ] **Последовательная загрузка моделей** (не держать все сразу): A → B → C-изоляция → C-сборка. Это упрощает код и потребление памяти.
* [ ] **Тестовый набор «золотых» компонентов** (Button, Card, Modal, Form, List) с ожидаемым кодом. Регрессионный тест после каждого изменения.
